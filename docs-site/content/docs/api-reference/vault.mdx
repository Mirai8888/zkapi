---
title: ZkApiVault
description: Native ETH settlement with note-bound Groth16 verification
---

The wallet calls `ZkApiVault` for native ETH deposits and withdrawals. It
accounts in whole gwei, with maximum amount `2^53 - 1`. The v2 vault pins
its Groth16 proof adapter, state-signing key, and clearance-signing key as
immutable constructor parameters. It has no XMSS root-rotation API.

This page describes the vault in this repository, which deployment manifests
declare as `vault_revision: 2`. Earlier deployed revisions require the exact
current root and permanently consume a challenged nullifier; their
`claimExpired` ignores pauses and their `setTreasury` takes effect at once. See
[Protocol](/docs/protocol#compatibility-and-trust).

## Deposit

| Field | Value |
|---|---|
| Method | `deposit(bytes32 commitment, uint128 amount, uint256[32] siblings)` (payable) |
| Caller | User's wallet, while not paused |
| Effect | Checks the empty-slot path against `currentRoot`, adds the note leaf, escrows the native ETH, and emits `NoteDeposited(noteId, commitment, amount, expiryTs, newRoot)` |

Here `commitment` is the Poseidon registration derived from the note secret,
not the anonymous balance commitment signed by the server. The deposited leaf
binds that registration, note ID, amount, and expiry. The note-bound circuit
includes this same leaf in each private balance commitment.

The transaction must send exactly `amount * nativeAssetWeiPerUnit` wei;
`nativeAssetWeiPerUnit` is one gwei and `billingToken` is the zero-address
native-asset sentinel. Only deposits carry transaction value. The on-chain
event supplies the actual expiry, rounded up to the vault's one-day expiry
bucket.

## Mutual close

| Field | Value |
|---|---|
| Method | `mutualClose(WithdrawalPublicInputs inputs, bytes proof, uint256[32] siblings)` |
| Caller | User's wallet or another transaction submitter, while not paused |
| Effect | Verifies the withdrawal proof with `hasClearance = true`, checks deployment and immutable signing-key bindings, requires a nonzero destination and a known `activeRoot`, removes the leaf at the current root, consumes the nullifier, closes the note, and pays the user and treasury |

The withdrawal's Schnorr clearance and state signatures are private proof
witnesses. `WithdrawalPublicInputs` contains these 14 fields in order:

```text
protocolVersion, chainId, contractAddress, activeRoot,
stateSigningKeyX, stateSigningKeyY,
clearanceSigningKeyX, clearanceSigningKeyY,
noteId, finalBalance, destination, withdrawalNullifier,
hasClearance, withdrawalTag
```

`proof` is the decoded 256-byte Groth16 artifact described in the
[API overview](/docs/api-reference). The user receives `finalBalance` billing
units; the treasury receives `depositAmount - finalBalance`. The vault
multiplies both amounts by `nativeAssetWeiPerUnit` before paying ETH.

`activeRoot` must satisfy `isKnownRoot(activeRoot)`: it is `currentRoot`, or a
root replaced within `ROOT_HISTORY_WINDOW` (one day of wall-clock time,
recorded in `rootRetiredAt(root)`). Otherwise the call reverts `UnknownRoot()`.
The `siblings` must reproduce the **current** root; stale siblings revert
`StaleRoot()` and can be replaced with a fresh path for the same proof. A
zero destination reverts `InvalidDestination()`. A nullifier recorded in
`challengedNullifiers` can still close with a valid clearance.

## Initiate escape withdrawal

| Field | Value |
|---|---|
| Method | `initiateEscapeWithdrawal(WithdrawalPublicInputs inputs, bytes proof, uint256[32] siblings)` |
| Caller | User's wallet or another transaction submitter, while not paused |
| Effect | Verifies a withdrawal proof with `hasClearance = false`, removes the leaf at the current root, consumes the nullifier, and stores the payout and `challengeDeadline = now + challengePeriod` |

The challenge period is configured at deployment; the default constant is 24
hours. No payout occurs until finalization. The call reverts
`InvalidDestination()` for a zero destination, `ChallengedNullifier()` when an
earlier escape at the same nullifier was challenged, `UnknownRoot()` for an
unknown `activeRoot`, and `StaleRoot()` for siblings that do not match the
current root.

## Challenge a stale escape withdrawal

| Field | Value |
|---|---|
| Method | `challengeEscapeWithdrawal(uint32 noteId, RequestPublicInputs inputs, bytes proof, uint256[32] siblings)` |
| Caller | Anyone with valid archived request evidence, before the deadline, including while paused |
| Effect | Verifies the archived request proof and its matching nullifier, restores the note's leaf, returns it to `Active`, cancels the pending withdrawal, clears `usedNullifiers[nullifier]`, sets `challengedNullifiers[nullifier]`, and emits `EscapeWithdrawalChallenged(noteId, nullifier, restoredRoot)` |

Submit the original request's public inputs, including its historical root.
The root may differ from the current root or the root when the escape began:
unrelated deposits or closes must not invalidate archived evidence. The
request nullifier must equal the pending withdrawal's nullifier. A later
signature alone is not challenge evidence.

The `siblings` argument is a fresh path for the empty slot at the **current**
root so the contract can restore the leaf. If another transaction changes the
root first, the challenge reverts `StaleRoot()`; resubmit it with a fresh path
before the deadline. The challenge cancels the stale withdrawal; it does not
slash or pay out the note.

A challenged nullifier can never back another escape, but it can still close
with a clearance. The owner normally withdraws from the server-signed
successor state instead. The note's expiry claim is pushed back so that at
least one `challengePeriod` of unpaused time remains after the challenge.

## Finalize escape withdrawal

| Field | Value |
|---|---|
| Method | `finalizeEscapeWithdrawal(uint32 noteId)` |
| Caller | Anyone at or after the stored deadline, including while paused |
| Effect | Closes the note and pays the destination and final balance already recorded during initiation, with the remainder paid to treasury |

## Claim expired note

| Field | Value |
|---|---|
| Method | `claimExpired(uint32 noteId, uint256[32] siblings)` |
| Caller | Anyone at or after `effectiveExpiry(noteId)`, while not paused |
| Effect | Removes an active note's leaf, closes the note, and pays its full deposit to treasury |

`notes(noteId)` keeps the nominal `expiryTs` used by the request proof.
`effectiveExpiry(noteId)` adds all paused time since the deposit and any
post-challenge grace, and is never earlier than `unpauseClaimGrace` after the
latest unpause. Before then the call reverts `NoteNotExpired()`. The view
assumes no further pause and returns zero for an unknown note.

## Owner controls

| Method | Caller | Effect |
|---|---|---|
| `pause()` | Owner, while not paused | Blocks deposits, `mutualClose`, `initiateEscapeWithdrawal`, `claimExpired`, `setTreasury`, `acceptTreasury`, `withdrawTreasuryArrears` and `renounceOwnership`; emits `Paused(account)` |
| `unpause()` | Owner, while paused (else `NotPaused()`) | Adds the pause to `totalPausedDuration`, sets `lastUnpausedAt`, and emits `Unpaused(account)` |
| `setTreasury(address)` | Owner, while not paused | Schedules a nonzero `pendingTreasury` other than the vault, ready at `pendingTreasuryReadyAt`; emits `TreasuryChangeScheduled(newTreasury, readyAt)` |
| `acceptTreasury()` | Owner, while not paused | Applies the scheduled treasury once ready; emits `TreasurySet(newTreasury)` |
| `cancelTreasuryChange()` | Owner, at any time | Clears the scheduled change; emits `TreasuryChangeCancelled(cancelledTreasury)` |
| `withdrawTreasuryArrears()` | Anyone, while not paused | Pays `treasuryArrears` to the current treasury; emits `TreasuryArrearsPaid(treasury, amount)` |
| `transferOwnership(address)` | Owner, at any time | Ownable key rotation |
| `renounceOwnership()` | Owner, while not paused | Ownable renunciation |

Pauses are unbounded; they freeze exits but cannot move user funds.
`readyAt` and `pendingTreasuryReadyAt` count on the vault's active clock (wall
clock minus all paused time), so a change waits `treasuryChangeDelay` of
unpaused time. `acceptTreasury()` reverts `NoPendingTreasuryChange()` without a
scheduled change and `TreasuryChangeNotReady()` before it is ready.

Treasury payments forward `TREASURY_PAYOUT_GAS` (100,000). A treasury that
reverts or needs more gas does not block the user's payout or an expiry claim:
its share is added to `treasuryArrears` (gwei units) and
`TreasuryPaymentDeferred(treasury, amount)` is emitted. A caller cannot force
that deferral by limiting gas; the whole transaction reverts instead.

## Deployment compatibility

The verifier must match circuit revision `zkapi-v2-note-bound-v1` and the
selected setup. The vault's adapter and signing keys are immutable. The server,
frontend, deployment manifest and proof assets must match these deployed
values, and clients must independently pin the trusted configuration. The
deployment script requires an explicit `OWNER` outside local chains and
records `owner`, `treasuryChangeDelay` and `rootHistoryWindow` in its output.
