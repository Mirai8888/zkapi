The browser SDK generates note-bound Groth16 proofs locally. `serverd`
verifies lease authorizations and signs balance updates, `indexerd` mirrors
the active note tree, and the native ETH vault settles withdrawals.
`zkapi-challenged` submits evidence against escape withdrawals from already-used
states. The host application owns the user interface.

  zkapi-indexerd                # Active note tree from on-chain events

The protocol Rust workspace is separate from the application workspace.
`zkapi-serverd` exports `processor_v2.rs` and `signer_v2.rs`. The native wallet
library is available in `protocol/rust/crates/zkapi-client`.

## Wallet and proof generation

The browser SDK stores private note state and pending-operation journals in
browser storage and runs the v2 prover through WASM. Its bundled setup assets
must match the circuit revision and selected deployment.

The wallet creates the complete authorization and saves it before sending.
The journal retains the original proof, public inputs, payload and request ID
needed for exact recovery. After receiving a finalized settlement response, it
checks the response hash, charge, Schnorr signature and note-bound commitment
update before saving the next state.

In the same storage transaction as the journal, the SDK appends the request to
an archive of transmitted requests. A server error alone never discards a
journal: on `stale_root` the SDK first rereads the vault root and the server's
nullifier record, and a discarded journal stays whole in the archive while the
note state is current, so a receipt finalized later still installs. Before an
escape it consults that archive, because an escape from a state that already
authorized a request can be challenged. For vaults declared as
`vault_revision: 2` it may escape from such a state once the server reports
the nullifier `unknown` or `clearance_reserved`, or through an explicit,
time-gated override; for other vaults it refuses. Only a receipt that verifies
vetoes that override. When the server claims a finalized receipt the browser
cannot apply (`receipt_journal_missing`), the override stays available behind
that case's own warning and acknowledgement, because a genuine claim makes the
escape's challenge certain. The claim stands until a reading saved after it
reports the nullifier `unknown` or `clearance_reserved`. The archive orders
saved readings by a sequence number stamped in its write transaction, never by
the device clock. See `sdk/README.md` for the exact codes and configuration.

## Server and verification

The server loads the request and withdrawal verifying keys, initializes
separate Schnorr state and clearance signers, opens its durable nullifier
store, and polls the indexer for the active root. Startup requires native
oracle configuration and a lease issuer. Both signing seeds are required, and
the published development keys are refused. Before opening its database for
writes, the server checks that the native billing RPC serves the configured
chain and that the derived keys equal the vault's immutable keys, then records
that binding; a restart with a matching record re-verifies it in the
background. Its advertised signing keys must also match the keys pinned in the
client configuration.

| Component | Responsibility |
|---|---|
| Groth16 request verifier | Membership, private signed-state validity, solvency, nullifier and authorization relation |
| Request processor | Deployment/key checks, payload and quote binding, freshness, current root, caps and durable reservation |
| Lease service | Issue a spending-limited runtime key, settle measured usage after retirement, and finalize every lease by a write-once deadline |
| Schnorr signer | Sign the updated commitment and anchor; sign clearance separately |
| Groth16ProofAdapter | Verify request challenge proofs and withdrawal proofs directly on-chain |
| Challenge service | Read pending escapes, use finalized authorization transcripts as evidence, submit EIP-1559 challenges before the deadline, and report each obligation's status |

## Deposit flow

1. The wallet samples a secret and computes the v2 registration commitment.
2. It obtains the next note ID and an empty-slot path from the indexed tree.
3. The user calls `deposit(commitment, amount, siblings)` on the pinned vault
   with exactly `amount × 1 gwei` in transaction value.
4. The vault emits `NoteDeposited` with the registration commitment, amount,
   expiry and new root; the indexer updates its tree.
5. The wallet confirms the note and initializes its random blinding and
   commitment `C = D·G + r·H + L·J`.

Only the registration commitment goes to the vault. The secret stays with the
wallet, and the note-bound balance commitment is used for private state proofs.
The SDK can derive sibling paths from a whole-tree snapshot without querying
an individual note ID; see the [indexer API](/docs/api-reference/indexer).

## Authenticated usage

```mermaid
sequenceDiagram
  participant B as Browser SDK
  participant I as Indexer
  participant S as Billing server
  participant O as OpenRouter
  B->>I: Active tree snapshot
  I-->>B: Root and leaves
  B->>S: GET /v2/billing/quote
  S-->>B: Native ETH billing quote
  B->>B: Verify quote, prove and journal authorization
  B->>S: POST /v2/openrouter/leases
  S->>S: Verify proof and quote; reserve nullifier
  S-->>B: Short-lived runtime key
  B->>O: Direct inference calls
  O-->>B: Inference responses
  B->>S: Retire lease with original authorization
  S->>S: Complete retirement and usage settlement
  B->>S: Recover signed settlement
  S-->>B: Charge, next commitment, anchor, Schnorr signature
  B->>B: Verify and save next private state
```

The authorization payload contains no prompt. The accepted native ETH quote
is bound into that payload and stays fixed through recovery and settlement.
One lease can cover multiple inference calls; its next signed balance arrives
after retirement and settlement, rather than after each provider response.

## Withdrawal and challenges

For mutual close, the wallet proves note ownership with an escape-form
withdrawal proof for its destination and current balance, and sends it to
`POST /v2/withdraw/clearance` for a Schnorr clearance signature. It then proves
the final balance, destination and clearance mode a second time, with the
signature as a private witness, and submits
`mutualClose(inputs, proof, siblings)`. The vault accepts a proof root that is
current or was replaced within the last day, checks the siblings against the
current root, removes the leaf and pays out native ETH.

An escape uses a withdrawal proof without clearance. The challenge service
uses the archived request proof and its original historical root to show that
the withdrawal nullifier already authorized usage. It uses a request only
after the server finalizes its settlement. It obtains a fresh zero-slot path
to restore the note in the current tree. Other deposits and closes do not
require rewriting the old proof's root. A successful challenge releases the
nullifier but blocks every later escape at it; the owner withdraws from the
signed successor state. See [Protocol](/docs/protocol#withdrawal) and the
[vault API](/docs/api-reference/vault).

The challenge service serves `/livez`, `/health` and `/status` on a private
listener, raises each obligation's severity as its deadline approaches, and
signs through a restricted EIP-1559 signer. See the
[challenge service operation](https://github.com/ethereum/zkapi/blob/main/docs/challenge-service.md)
guide.

## Deployment identity

A deployment fixes the chain, vault, proof adapter, state signing key and
clearance signing key. Clients must pin the circuit revision, matching proof
assets and deployment identity; fetching a manifest is not enough to establish
trust in its contents. Mainnet and Sepolia have independent pins and wallet
state. A pinned manifest may also declare `vault_revision` and
`clearance_ownership_proof`, which select the wallet's escape and clearance
behavior. See
[setup and compatibility](/docs/cryptography#setup-and-compatibility) for the
setup trust assumptions and artifact compatibility requirements, and
[owner and operator powers](/docs/protocol#owner-and-operator-powers) for what
the vault owner and the operator can do.
