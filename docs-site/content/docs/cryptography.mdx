## Current cryptographic suite

The active v2 implementation uses **Groth16 over BN254**, with Poseidon hashes
and Baby-JubJub commitments and signatures. The circuit revision is
`zkapi-v2-note-bound-v1`. The browser SDK proves native ETH lease
authorizations locally using the packaged WASM and matching proving keys.

| Component | Current implementation |
|---|---|
| Proof system | Separate request and withdrawal Groth16 circuits over BN254 |
| Circuit field | BN254 scalar field |
| Hash function | Poseidon: exponent 5, 8 full rounds, 57 partial rounds, rate 2, capacity 1 |
| Active-note tree | Depth-32 Merkle tree with domain-separated Poseidon nodes and zero leaf 0 |
| Balance commitment | Note-bound Pedersen commitment on Baby-JubJub |
| State and clearance signatures | Poseidon-challenged Schnorr on Baby-JubJub, with separate signing keys |
| Nullifiers and authorization tags | Domain-separated Poseidon |
| Payload and request-context digests | Domain-separated Keccak-256 hash-to-field encoding |

This suite is **not post-quantum**. Groth16/BN254 and the Baby-JubJub commitment
and signature schemes rely on elliptic-curve assumptions.

The Rust type `Felt252` encodes a canonical, big-endian BN254 scalar-field
element. JSON uses checked
hexadecimal strings.

## Binding a balance to its note

Let `s` be the user's secret, `D` the deposit, `B` the current balance, `r` the
blinding scalar and `τ` the current state anchor. `domain(label)` encodes the
label bytes as a field element. The registration commitment and active-note
leaf are:

```text
registration = Poseidon(domain("zkapi.v2.reg"), s, 0)
L = Poseidon(domain("zkapi.v2.leaf"), note_id, registration, D, expiry)
C = B·G + r·H + L·J
```

The request and withdrawal circuits compute `L` from the same note
values used in the Merkle-membership proof, then use that leaf in the signed
balance commitment. Binding the signed balance to `L` prevents a signature
from being transplanted to a different active note.

`G` is the standard Baby-JubJub generator. `H` and `J` are independently derived
by Keccak-256 try-and-increment, selecting even `y` and clearing the cofactor,
from these distinct labels:

- `H`: `zkapi.v2.balance.blinding.generator`
- `J`: `zkapi.v2.note-binding.generator.v1`

Neither is constructed as a known scalar multiple of another generator. Both
native code and the circuit multiply `J` by the full canonical BN254 field
representation of `L`, implicitly reducing it modulo the subgroup order.
Fresh random blinding hides the leaf contribution in the public commitment.

Rerandomization and server charging preserve that note binding:

```text
C_anon = C + ε·H
C_next = C_anon − charge·G + blind_delta·H
B_next = B − charge
r_next = r + ε + blind_delta
```

The client samples `ε`; the active server samples `blind_delta` as a random
scalar. Blinding arithmetic is modulo the Baby-JubJub subgroup order. The
server can update the anonymous commitment without learning `B`,
`r` or `L`. The client verifies the returned signature and commitment update
before saving the next state.

## State, request and withdrawal binding

The server signs a Poseidon digest of the protocol version, chain ID, vault
address, commitment coordinates and anchor under `zkapi.v2.state`. The circuit
verifies that Schnorr signature privately. The genesis path instead proves
`B = D` and `τ = 1`; the client initializes it with random blinding.

Each state has one nullifier, independent of the request payload:

```text
x = Poseidon(domain("zkapi.v2.null"), s, τ)
authorization_tag = Poseidon(domain("zkapi.v2.auth"), x, request_context)
```

The request context commits to the exact client request ID and payload digest.
In the native ETH flow, this is the prompt-free lease authorization payload,
including its pinned billing quote. The server recomputes the context and
checks the authorization tag, proof, deployment identity, current root, signing
key, freshness window, charge cap and nullifier reservation. It separately
validates the quote identity and freshness. This binds the proof to the exact
lease authorization while keeping the nullifier the same for any attempt to
spend that state again.

Clearance uses a separate Schnorr key to sign the protocol version, chain ID,
vault address and withdrawal nullifier under `zkapi.v2.clear`. Mutual-close
proofs verify this signature inside the circuit. Escape proofs use the same
withdrawal circuit with `has_clearance = false`, and follow the vault's
challenge process described in [Protocol](/docs/protocol). The server signs a
clearance only after verifying an escape-form withdrawal proof for the same
nullifier and deployment keys, which proves knowledge of the note secret,
unless it runs with the transitional `--allow-legacy-clearance` setting. A
request proof is never accepted for this. That ownership proof is itself a
valid escape input for its destination and balance.

The withdrawal tag binds the nullifier to the payout destination, final
balance and clearance mode:

```text
withdrawal_tag = Poseidon(domain("zkapi.v2.withdraw"), x_w, destination, B_final, has_clearance)
```

## Domain separation

The v2 Poseidon statements and helpers use these labels:

| Label | Usage |
|---|---|
| `zkapi.v2.reg` | Registration commitment |
| `zkapi.v2.leaf` | Active-note leaf |
| `zkapi.v2.node` | Merkle internal node |
| `zkapi.v2.null` | State nullifier |
| `zkapi.v2.auth` | Request authorization tag |
| `zkapi.v2.state` | State signature message |
| `zkapi.v2.clear` | Clearance signature message |
| `zkapi.v2.withdraw` | Withdrawal tag |
| `zkapi.v2.sig` | Schnorr challenge |
| `zkapi.v2.anchor` | Next anchor derivation |
| `zkapi.v2.blind` | Blinding-derivation helper; the active server samples its blinding delta randomly |

Byte payloads use a separate Keccak-256 encoding with length prefixes and a
counter for canonical field encoding: `zkapi.payload.v1` for request payloads,
`zkapi.response.v1` for response payloads, and `zkapi.v2.request-context` for
the request context. The `.v1` payload/response labels are intentionally
retained in v2; they are not Poseidon domain labels.

## Public and private proof inputs

The request proof has **12 public field elements**, in this exact order:

```text
protocol_version, chain_id, contract_address, active_root,
state_signing_key_x, state_signing_key_y, request_time, solvency_bound,
request_nullifier, authorization_tag,
anonymous_commitment_x, anonymous_commitment_y
```

Its private witness contains the secret, request context, note ID, deposit,
expiry, Merkle siblings, balance, blinding, rerandomization, anchor, genesis
flag and state signature. The circuit checks that the balance covers
`solvency_bound` and that the note expiry is at least `request_time`. On the
signed-state branch it does not bound the balance by the deposit; that bound
is a planned circuit change (see
[known limitations](/docs/protocol#known-limitations)).

The withdrawal proof has **14 public field elements**, in this exact order:

```text
protocol_version, chain_id, contract_address, active_root,
state_signing_key_x, state_signing_key_y,
clearance_signing_key_x, clearance_signing_key_y,
note_id, final_balance, destination, withdrawal_nullifier,
has_clearance, withdrawal_tag
```

Its private witness contains the secret, deposit, expiry, Merkle siblings,
final blinding, anchor, genesis flag, state signature and clearance signature.
The circuit also enforces that `final_balance` does not exceed the deposit.
Withdrawal intentionally reveals the note ID, final balance and destination:
to the server when a mutual close requests clearance, and on-chain when the
note closes.

“Private witness” describes what the proof reveals, not all surrounding
activity: deposits are on-chain, and the server receives the prompt-free lease
authorization and request ID. Inference prompts and responses go directly
between the browser and provider. Request proofs hide which deposited note is
being used, its exact balance and expiry, and the current signed state.

## Setup and compatibility

The note-bound circuit revision uses the v2 JSON schemas and public-input
order. Signed commitments, proving/verifying keys and deployed verifiers must
all match this circuit revision and setup.

Proving and verifying key files carry the `zkapi-v2-note-bound-v1` header, and
loaders reject incompatible files. Deployment manifests advertise
`proof_setup.circuit_id`; clients must also pin the key hashes and vault
address. The header catches accidental mismatches. It does not establish
setup provenance or replace independently pinned hashes.

The checked-in `protocol/setup/v2` artifacts are a **single-party setup
generated with OS randomness**. No multiparty ceremony has been conducted.
Matching hashes identify the artifacts; they do not establish that setup
secrets were destroyed. The circuit, generator derivation and setup require
independent review before production. The generated Solidity verifier,
native keys and browser WASM/proving-key assets must match the same revision
and setup.

The vault's proof adapter and signing keys are immutable. Configure the server,
client, verifier and proof assets to match the deployed vault, and verify the
client's deployment pins before funding a wallet.
