zkAPI lets users fund a private note with native ETH, then authorize off-chain
API usage with proofs generated in the browser. Each authorization consumes a
state nullifier; after usage settles, the server signs the next private balance
and anchor.

These docs describe **protocol v2**, circuit revision
`zkapi-v2-note-bound-v1`: Groth16 over BN254, Poseidon hashes, and Baby-JubJub
commitments with Schnorr signatures.

## How the pieces fit

**The wallet** keeps the secret, note metadata, balance, blinding, anchor, and
server signature locally. It proves active membership and sufficient funds,
then sends a nullifier, a rerandomized note-bound commitment, an authorization
tag, and a Groth16 proof. The browser SDK runs the prover in WASM, using the
same cryptographic libraries as the native Rust wallet library.

**`serverd`** verifies proofs, checks the deployment and active root, rejects
conflicting nullifier reuse, and signs balance updates with its Schnorr key.
It issues short-lived OpenRouter keys against proof-bound native ETH billing
quotes and settles their measured usage. Prompts and responses pass directly
between the client and OpenRouter.

**The vault, indexer, and challenge service** maintain the active note tree,
verify withdrawals on-chain, and challenge escape withdrawals from states
that already authorized usage.

## Privacy and deployment assumptions

Request proofs hide the note ID, deposit, exact balance, expiry, anchor, and
state signature. They do not hide information outside the proof: deposits and
withdrawals are public, network and timing metadata remain observable, and
the upstream provider sees prompts. Direct leases keep prompts out of the
billing authorization. A mutual close shows the server the note ID, final
balance and destination when it requests clearance.

The vault owner can pause deposits and exits without a time limit and
schedule time-locked treasury changes. In this repository's vault revision a
pause cannot move user funds or make notes expire. The operator signs every
balance update and clearance. See
[owner and operator powers](/docs/protocol#owner-and-operator-powers).

The current Groth16 and Baby-JubJub construction is not post-quantum. The
checked-in proving keys use a single-party setup with no multiparty ceremony;
artifact hashes establish identity, not setup security. See
[Cryptography](/docs/cryptography) for setup trust and compatibility requirements.
